# Складской учёт

Веб-приложение для учёта материалов, единиц измерения, поставщиков, поступлений на склад и расхода материалов со склада.

Проект выполнен в рамках лабораторной работы №1 по дисциплине DevOps.

---

## Возможности

- ведение справочника материалов и единиц измерения;
- ведение справочника поставщиков;
- регистрация поступлений материалов на склад;
- регистрация расхода (выдачи) материалов со склада;
- автоматический расчёт текущего остатка материала;
- просмотр состава приходных и расходных накладных;
- редактирование спецификации и описания материала;
- удаление материалов, поступлений и расходов;
- аутентификация по логину и паролю;
- роли `admin` и `warehouse_worker`;
- проверка бизнес-правил предметной области (контроль остатков, защита истории);
- PostgreSQL для хранения данных;
- служебный endpoint проверки работоспособности `/health`;
- конфигурация приложения через переменные окружения;
- веб-интерфейс на HTML/CSS/JavaScript;
- контейнеризация через Docker и Docker Compose.

## Роли и доступ

### Кладовщик (`warehouse_worker`)

- просматривает материалы и остатки;
- создаёт и удаляет поступления;
- создаёт и удаляет расходы;
- редактирует спецификацию материалов;
- работает со справочником поставщиков;
- не управляет пользователями.

### Администратор (`admin`)

- выполняет все операции кладовщика;
- дополнительно управляет пользователями и ролями;
- управляет деактивацией справочников.

Изменение данных через `POST`, `PUT` и `DELETE` требует аутентификации.  
Просмотр материалов и справочников доступен без авторизации.

## Основные сущности

В системе используются следующие основные сущности:

- `Role` — роль пользователя;
- `User` — пользователь системы;
- `MeasurementUnit` — единица измерения;
- `Supplier` — поставщик;
- `Material` — материал (с полем текущего остатка `quantity`);
- `Receipt` — документ поступления на склад;
- `ReceiptItem` — позиция документа поступления;
- `Issue` — документ расхода со склада;
- `IssueItem` — позиция документа расхода.

Схема базы данных описана в файле `SCHEMA.md`.

---

## Основные бизнес-правила

- количество материала в позиции поступления должно быть больше нуля;
- цена за единицу не может быть отрицательной;
- один материал не может дважды встречаться в одном поступлении;
- один материал не может дважды встречаться в одном расходе;
- нельзя выдать материала больше, чем есть на складе;
- номер документа поступления и расхода уникален;
- приход увеличивает остаток материала, расход уменьшает;
- удаление накладной прихода уменьшает остаток на её позиции;
- удаление накладной расхода возвращает материалы на склад;
- материал с историей движений нельзя удалить физически;
- материалы и поставщики с историей деактивируются, а не удаляются;
- после деактивации материала он не участвует в новых документах, но сохраняется в истории.

## Архитектура

Приложение разделено на слои:

```
Frontend
   ↓ HTTP
Routes (FastAPI)
   ↓
Schemas (Pydantic)
   ↓
Models (SQLAlchemy ORM)
   ↓
PostgreSQL
```

- `frontend` — HTML-шаблоны и JavaScript, которые обращаются к API через fetch;
- `routes` — принимают HTTP-запросы и валидируют данные;
- `schemas` — описывают входные и выходные данные API через Pydantic;
- `models` — описывают таблицы SQLAlchemy;
- `auth` — JWT-аутентификация и разграничение доступа;
- `database` — асинхронное подключение к PostgreSQL через asyncpg.

## Подготовка окружения

Проект рассчитан на запуск через **Docker Desktop** (Windows/macOS) или **Docker Engine + Docker Compose** (Linux).

Локально устанавливать Python и PostgreSQL не требуется — всё работает внутри контейнеров.

Необходимые порты:

- **8000** — приложение (FastAPI + веб-интерфейс);
- **5433** — PostgreSQL (проброшен из контейнера наружу, чтобы не конфликтовать с локальной БД, если она есть).

---

## Переменные окружения

Создать локальный `.env`:

```bash
cp .env.example .env
```

Пример содержимого:

```env
POSTGRES_USER=warehouse_user
POSTGRES_PASSWORD=secure_password_123
POSTGRES_DB=warehouse_db
POSTGRES_HOST=db
POSTGRES_PORT=5432

DATABASE_URL=postgresql+asyncpg://warehouse_user:secure_password_123@db:5432/warehouse_db

APP_HOST=0.0.0.0
APP_PORT=8000
SECRET_KEY=change_me_in_production
```

`.env` содержит локальные настройки и секреты и **не должен попадать в Git**.  
В репозитории хранится только `.env.example`.

## Запуск

Собрать и поднять контейнеры:

```bash
docker compose up -d
```

Проверить статус:

```bash
docker compose ps
```

После запуска:

- сайт: **http://localhost:8000**
- Swagger UI: **http://localhost:8000/docs**
- ReDoc: **http://localhost:8000/redoc**
- healthcheck: **http://localhost:8000/health**

Остановить:

```bash

```

```bash

```

## Аутентификация

Для входа используются логин и пароль.

Пароль хранится в БД в виде bcrypt-хэша.

После успешного входа сервер возвращает подписанный **JWT-токен**, который клиент сохраняет в `localStorage` и передаёт в заголовке:

```
Authorization: Bearer <token>
```

Неавторизованные пользователи могут просматривать материалы и справочники, но не могут создавать, редактировать или удалять данные.

## Проверка работоспособности

Служебный endpoint:

```

```

Пример успешного ответа:

```json

  "database": "connected",
  "version": "0.1.0"

```

## Git-процесс

Основной порядок внесения изменений:

```
Issue
  ↓
отдельная ветка
  ↓
несколько осмысленных коммитов
  ↓
Pull Request / Merge Request
  ↓

```

Прямой push в `main` запрещён.

---

## Правила внесения изменений

Перед слиянием изменений необходимо:

- убедиться, что приложение запускается (`docker compose ps`, `/health`);
- проверить изменённую функциональность в веб-интерфейсе;
- проверить `/health`;
- проверить, что `.env` и другие локальные файлы не добавлены в Git;
- просмотреть изменения в Pull Request;
- после проверки выполнить merge в `main`.

**Запрещается:**

- добавлять `.env`, пароли и другие секреты в репозиторий;
- вносить новую функциональность непосредственно в `main`, минуя отдельную ветку;
- выполнять merge непроверенного кода;
- удалять или ослаблять бизнес-проверки только ради успешного запуска;
- отключать тесты и линтеры, чтобы прошли проверки.
