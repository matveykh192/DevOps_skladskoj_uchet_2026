# Складской учёт

Учебная информационная система для учёта материалов на складе: справочники, поступления, расход, текущие остатки и предупреждения о недостаточном запасе.

Проект разработан по дисциплине **«Методологии и практики DevOps»** (2026 год). В репозитории объединены результаты лабораторных работ № 1–3: веб-приложение и база данных, развёртывание на Linux-серверах, автоматизированное тестирование и сопровождение.

## Возможности

- Учёт материалов, единиц измерения и поставщиков.
- Регистрация поступлений и расходных накладных.
- Пересчёт текущего количества материала при движении товаров.
- Контроль бизнес-правил: положительные количества, неотрицательные цены, недопустимость расхода сверх остатка, уникальность документов и сохранение истории операций.
- Авторизация с JWT, ролями `admin` и `warehouse_worker`.
- Просмотр и редактирование через веб-интерфейс.
- Индивидуальный минимальный запас `minimum_stock` для каждого материала.
- Предупреждение **«⚠ Мало»**, когда текущий остаток строго меньше индивидуального минимума.
- REST API, интерактивная документация и endpoint `/health`.
- Контейнеризация, миграции схемы, тестирование, статический анализ и резервное копирование.

## Основные сущности и бизнес-правила

| Сущность | Назначение |
|---|---|
| `Role`, `User` | Пользователи, роли и доступ |
| `MeasurementUnit` | Единицы измерения |
| `Supplier` | Поставщики |
| `Material` | Материалы, остаток `quantity`, минимум `minimum_stock` |
| `Receipt`, `ReceiptItem` | Поступления и позиции документов |
| `Issue`, `IssueItem` | Расход и позиции документов |

Ключевые правила предметной области:

- количество позиции документа должно быть больше нуля;
- цена поступления не должна быть отрицательной;
- один материал не должен дублироваться в позициях одного документа;
- при расходе нельзя выдать больше имеющегося остатка;
- номера документов уникальны;
- поступление увеличивает остаток, расход уменьшает его;
- отмена или удаление документов корректирует остатки по предусмотренным правилам приложения;
- история движения материалов должна сохраняться, в том числе при деактивации справочных записей;
- `minimum_stock` неотрицателен и **не блокирует операции**, а служит предупреждением.

Для последнего правила используется строгое сравнение:

```python
is_below_minimum = bool(minimum_stock and quantity < minimum_stock)
```

При остатке `4` и минимуме `5` отображается «⚠ Мало», а при остатке `4` и минимуме `4` предупреждения нет. Прежний отчёт по ручному порогу остатка работает независимо от индивидуального минимума.

## Быстрый запуск (Docker Desktop)

Нужны Docker Desktop с поддержкой Docker Compose и GNU Make. Команды приведены для **PowerShell из корня репозитория**; на Linux команды Docker и Make аналогичны.

### 1. Подготовка образов

```powershell
make setup
```

`make setup` **собирает образы** приложения и тестового окружения. Команда не создаёт таблицы PostgreSQL и не запускает сам сервис.

### 2. Запуск PostgreSQL

```powershell
docker compose up -d db
docker compose ps
```

В стандартной локальной конфигурации приложение доступно на `127.0.0.1:8000`, PostgreSQL — на `127.0.0.1:5433`; внутри сети Compose база слушает порт `5432` и доступна приложению под именем `db`.

**Важно:** основная база хранится в Docker-томе `postgres_data`. Старый `db/init.sql` сохранён как исторический материал, но текущая конфигурация **не выполняет его автоматически**: схему создаёт Alembic.

### 3. Миграции (только для новой, пустой базы)

Перед изменением уже существующей базы сначала создайте резервную копию и проверьте текущую версию схемы. Применять исходную миграцию к таблицам, созданным старым `init.sql`, без аудита нельзя.

Для новой пустой БД:

```powershell
docker compose run --rm --no-deps -e WAREHOUSE_ALLOW_MIGRATE=YES_I_HAVE_A_BACKUP app python -m alembic upgrade head
```

Переменная `WAREHOUSE_ALLOW_MIGRATE` — намеренное подтверждение изменения основной БД. Она не создаёт резервную копию автоматически.

Проверка версии:

```powershell
docker compose exec -T db psql -U warehouse_user -d warehouse_db -c "SELECT version_num FROM alembic_version;"
```

Ожидаемая актуальная ревизия: `003_minimum_stock`.

### 4. Создание учебного администратора и справочников

После миграций выполните команду начального заполнения (для PowerShell):

```powershell
$env:DEMO_ADMIN_USERNAME = 'admin'
$env:DEMO_ADMIN_PASSWORD = Read-Host 'Пароль администратора (от 8 символов)'
docker compose run --rm --no-deps -e DEMO_ADMIN_USERNAME -e DEMO_ADMIN_PASSWORD app python -m scripts.seed_demo
Remove-Item Env:DEMO_ADMIN_PASSWORD
Remove-Item Env:DEMO_ADMIN_USERNAME
```

Скрипт `scripts/seed_demo.py` подготавливает роли, единицы измерения и учебного администратора. Используйте собственный пароль; он не должен быть записан в README или опубликован в Git. Для уже заполненной БД повторять миграции и инициализацию без необходимости не нужно.

### 5. Запуск приложения

```powershell
make run
docker compose ps
```

Открыть:

- Интерфейс материалов: **http://localhost:8000/materials**
- Страница входа: **http://localhost:8000/login**
- Swagger API: **http://localhost:8000/docs**
- ReDoc: **http://localhost:8000/redoc**
- Проверка состояния: **http://localhost:8000/health**

Для диагностики:

```powershell
docker compose logs --tail=80 app
```

Для остановки:

```powershell
make down
```

Не используйте `docker compose down -v` для обычной остановки: ключ `-v` удаляет тома и может привести к потере данных. Страница `/` в текущей реализации не является основным экраном; для входа используйте адреса выше.

## Лабораторная работа № 2: Linux-развёртывание

В проекте сохранены скрипты `deploy/` для сценария развёртывания на двух Linux-серверах: отдельный сервер приложения и отдельный сервер PostgreSQL. Развёртывание включает настройку служб и сетевого доступа; подробности представлены в `deploy/README.md`.

**Локальный Docker Compose и Linux-развёртывание — разные сценарии.** Команды `make verify`, `make backup` и `make restore`, описанные здесь, относятся к локальной Docker-конфигурации и не должны применяться к Linux-серверам без отдельной настройки.

## Лабораторная работа № 3: тестирование и сопровождение

### Независимое тестовое окружение

Тесты запускаются через `docker-compose.test.yml` с отдельным именем проекта Compose — `warehouse-lr3-test`. Они используют независимую PostgreSQL и **не должны обращаться к основной `warehouse_db`**.

```powershell
make test
```

Тесты включают проверки API и бизнес-правил, ошибочных и граничных входных данных, целостности операций и новой функции минимального запаса. Проверка требований предметной области отдельно описана в `docs/LR3-TEST-MATRIX.md`.

### Проверки качества и безопасности

```powershell
make quality
make sast
make verify
```

`make verify` объединяет Ruff, Ruff format, Bandit, pytest с покрытием, проверку миграций и восстановление тестового дампа. Ошибка любого этапа останавливает проверку; нельзя отключать проверки, пропускать тесты или искусственно снижать порог покрытия ради зелёного результата.

Bandit сейчас запускается с параметром `-ll`, то есть проверяет находки **средней и высокой степени серьёзности**. Это ограничение указано явно; оно не эквивалентно полному аудиту безопасности.

Зафиксированный результат последней успешной проверки (14 октября 2026 года):

| Проверка | Результат |
|---|---|
| Ruff lint | Успешно |
| Ruff format | 19 файлов соответствуют формату |
| Bandit (`-ll`) | Найденных проблем нет |
| pytest | **52 теста пройдены** |
| Покрытие Python-кода с ветвлениями | **65,13%** при пороге **60%** |
| Миграции: пустая БД | Успешно: 001 → 002 → 003 |
| Миграции: заполненная БД | Данные и остатки сохранены |
| Сценарий повреждения и восстановления | Успешно |

В ходе тестов выводились пять предупреждений об устаревающих интерфейсах Pydantic/FastAPI; они не были подавлены и не приводили к падению тестов. Число 65,13% — показатель покрытия **исходного Python-кода**, а не автоматическое доказательство покрытия 65,13% требований ТЗ.

XML-отчёты `reports/junit.xml` и `reports/coverage.xml` генерируются автоматически и не включаются в Git.

### Миграции Alembic

| Ревизия | Содержание |
|---|---|
| `001_baseline` | Начальная схема PostgreSQL для пустой БД |
| `002_stock_integrity` | Ограничения корректности количества и цен |
| `003_minimum_stock` | Добавление индивидуального порога `minimum_stock` |

```powershell
make migration-check
```

Проверяются два сценария: создание с нуля и переход существующей заполненной схемы с сохранением данных. Подробности — в `docs/LR3-MIGRATIONS.md`.

### Мутационный тест

Чтобы проверить чувствительность автоматических тестов к дефекту, в свойстве `is_below_minimum` намеренно заменяли `<` на `<=`. Тест `test_boundary_exactly_equal_is_not_low` обнаружил ошибку: на равенстве остатка и минимального запаса ошибочная реализация возвращала `True` вместо ожидаемого `False`.

В PowerShell:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\check_mutation.ps1
```

Сценарий выполняется на изолированной тестовой БД. После эксперимента исходный файл восстанавливается с проверкой SHA256; результат сохраняется в `reports/mutation-test.txt`. **Падение целевого теста во время активной мутации ожидаемо**; итоговая проверка должна подтвердить восстановление исходного кода.

### Резервное копирование и восстановление

Для основной учебной БД:

```powershell
make backup
make restore
```

- `make backup` создаёт архив `backups/warehouse_db.dump` в формате PostgreSQL custom (`pg_dump -Fc`).
- `make restore` восстанавливает его в **отдельную контрольную БД**, проверяет версию `003_minimum_stock` и наличие материалов, после чего удаляет контрольную БД. Основная `warehouse_db` не изменяется.

Для независимого теста повреждения:

```powershell
make backup-check
```

Контрольная база `warehouse_backup_verify` создаётся в тестовом PostgreSQL. Сценарий сохраняет материал с остатком `12.500` и минимумом `5.000`, удаляет его, восстанавливает архив и сверяет значения и ревизию Alembic.

Команда `make restore-main` предназначена для **реального восстановления основной БД с её пересозданием**. Её нельзя использовать для обычной проверки: она разрушительна и требует отдельного подтверждения и актуальной резервной копии.

Подробнее: `docs/backup-restore.md`.

## Проверка новой функции в браузере

После запуска приложения и входа:

1. Создайте материал или откройте существующий с количеством `4`.
2. Укажите минимальный запас `5`: в списке материалов появится **«⚠ Мало»**.
3. Измените минимальный запас на `4`: предупреждение исчезнет.
4. Проверьте поступление и расход материала: фактический остаток должен измениться соответствующим образом.

Это отдельная ручная проверка пользовательского интерфейса в дополнение к автоматическим тестам.

## Git и правила внесения изменений

Изменения выполняются в отдельных ветках (например, `feature/lab3-testing-foundation`) с последующей проверкой и Pull Request. Не следует делать прямой push в основную ветку без принятого в проекте процесса проверки.

Перед коммитом:

```bash
git status --short --untracked-files=all
git diff --check
git diff --cached --check
```

Не включайте в коммит дампы БД, локальный `.env`, отчёты сгенерированных проверок, временные архивы и пароли. Тесты и линтеры нельзя обходить или отключать ради прохождения проверки.
