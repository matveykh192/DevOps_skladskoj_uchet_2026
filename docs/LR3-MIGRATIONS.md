# ЛР №3: Alembic — миграции схемы БД

## Три ревизии

- `001_baseline`: девять таблиц складского учёта и представление `v_material_balances` для пустой БД.
- `002_stock_integrity`: ограничения корректности остатков, количеств и стоимости.
- `003_minimum_stock`: `materials.minimum_stock NUMERIC(12,3) NOT NULL DEFAULT 0` и запрет отрицательного значения. Реализация UI/API — следующая часть ЛР.

## Как проверить (PowerShell)

`make migration-check` — запускает проверку через тестовый контейнер, создавая ДВЕ отдельные временные БД `warehouse_migration_clean` и `warehouse_migration_filled` на сервере `test-db`. Основную БД `warehouse_test_db` тесты не трогают. Первая БД получает все три ревизии на чистой схеме; во второй создаётся старая ORM-схема и контрольные записи, затем выполняются `stamp 001_baseline`, переход на `head` и сверка остатков.

`make verify` включает этот тест миграций после Ruff, Bandit и pytest. В случае ошибки проверка останавливается.

## Существующие данные и ЛР №2

НИКОГДА не запускайте `upgrade head` вслепую на уже существующей БД без `alembic_version`: `001_baseline` пытается создать таблицы заново. `stamp 001_baseline` допустим **только после резервной копии и отдельной проверки схемы**. SQL-файлы `db/init.sql`, `db/init-standalone.sql` и ORM имеют отличия; скрипт здесь проверяет именно ORM-совместимый заполненный сценарий, но НЕ объявляет произвольную БД ЛР №2 безопасной для `stamp`. Для реального переноса сначала выполняется проверка структуры и данных, затем резервное копирование. Команды миграции защищены переменной `WAREHOUSE_ALLOW_MIGRATE=YES_I_HAVE_A_BACKUP` вне тестового окружения.

`minimum_stock` пока не добавлен в ORM: до следующей части нельзя пользоваться этим полем через API. Сами миграции и сохранность данных можно проверять независимо.
