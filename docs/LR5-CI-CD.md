# Документация по Лабораторной работе №5: Непрерывная интеграция (CI)

## 1. Выбранный стек CI/CD
Для организации пайплайна непрерывной интеграции выбран **GitHub Actions**:
- Не требует выделенных мощностей и 16 GB RAM (в отличие от локального GitLab).
- Нативно интегрирован с репозиторием на GitHub.
- Имеет встроенный реестр образов: **GitHub Packages (GHCR - GitHub Container Registry)**.

---

## 2. Структура пайплайна (`.github/workflows/ci.yml`)

Пайплайн разбит на независимые этапы (jobs) с контролем зависимостей (`needs`):

```
       [ secret-scan ] (gitleaks)
             │
             ├───────────────────┬──────────────────┐
             ▼                   ▼                  ▼
     [ quality (ruff) ]   [ security (sast) ]  [ container-check ]
             │                   │                  │
             └───────────────────┼──────────────────┘
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
      [ tests (pytest) ]               [ migrations ] & [ backup-restore ]
                 │                               │
                 └───────────────┬───────────────┘
                                 ▼
                     [ scan-image (trivy) ]
                                 │
                                 ▼
                     [ publish (ghcr.io) ]  <-- только если ветка main и все проверки PASS
```

### Этапы (Jobs):
1. **`secret-scan`**: Поиск случайно закоммиченных паролей и приватных ключей с помощью **Gitleaks**.
2. **`quality`**: Проверка линтером `ruff check` и проверка форматирования `ruff format --check`.
3. **`security`**: Статический анализ кода на уязвимости (**Bandit**) и аудит безопасности зависимостей (**pip-audit**).
4. **`container-check`**: Запуск проверочного скрипта `scripts/container_check.py` (запрет `:latest`, запрет root, проверка портов, лимитов памяти/процессора и сигналов).
5. **`tests`**: Выполнение unit- и интеграционных тестов в изолированном стеке Compose (`docker-compose.test.yml`) на чистой тестовой базе PostgreSQL. Сохранение отчетов `reports/junit.xml` и `reports/coverage.xml` в артефакты CI.
6. **`migrations`**: Проверка применения миграций Alembic на чистой и на заполненной БД (`scripts/check_migrations.py`).
7. **`backup-restore`**: Автоматическое создание бэкапа, симуляция удаления данных и восстановление (`scripts/backup_restore.py check`).
8. **`scan-image`**: Сборка Docker-образа и его сканирование анализатором уязвимостей контейнеров **Trivy**.
9. **`publish`**: Логин в реестр `ghcr.io`, присвоение образу тега с хэшем коммита (Commit SHA: `ghcr.io/username/repo:<sha>`) и публикация. Запускается **только при успешном прохождении всех предыдущих проверок** и только в ветке `main`.

## 3. Защита критических файлов приемки
1. **Файл `.github/CODEOWNERS`**:
   - Назначает владельца (`@matveykh192`) ответственным за тесты (`/tests/`), конфигурации CI (`/.github/`), сборочные скрипты (`/Makefile`, `/scripts/`) и правила анализаторов.
2. **Правила защиты веток (Branch Protection Rules в GitHub)**:
   - Ветка `main` закрыта от прямых пушей (`git push origin main` запрещен).
   - Изменения вносятся только через Pull Request.
   - Обязателен аппрув владельца (Code Owner Review) при изменении критических файлов.
   - Обязателен успешный прогон всех проверок CI (Status checks must pass).

---

## 4. Сценарии проверки на защите

### 1) Остановка pipeline при поломке теста или миграции:
- Вносим мутацию в `app/models.py` (меняем `<` на `<=`).
- Делаем пуш в PR.
- Пайплайн падает на этапе `unit & integration tests`, горит красный крест.
- Этапы `scan-image` и `publish` не запускаются.

### 2) Обнаружение тестового секрета:
- Добавляем в код строчку с фейковым токеном: `API_KEY = "ghp_ABCDEFGHIJKLMNOPQRSTUVWXYZ1234567890"`.
- Этап `secret-scan` (Gitleaks) немедленно падает с ошибкой обнаружения утечки секрета.

### 3) Подтверждение блокировки публикации:
- При любой ошибке в тестах или безопасности стадия `publish` отменяется благодаря директиве `needs: [tests, migrations, backup-restore, scan-image, secret-scan]`. Образ в реестр не отправляется.

### 4) Защита критических файлов:
- Показываем преподавателю файл `.github/CODEOWNERS`. Любая попытка удалить тест или ослабить проверку в `Makefile` требует согласования ответственного.

### 5) Почему локальные и серверные проверки должны совпадать:
- Паритет окружений (Environment Parity) предотвращает ситуацию «на моём компьютере работало, а на сервере упало». Разработчик прогоняет `make verify` локально перед отправкой кода и уверен, что CI на сервере отработает успешно.
